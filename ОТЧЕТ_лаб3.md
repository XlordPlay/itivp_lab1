## 1 ЦЕЛЬ РАБОТЫ

## 2 КРАТКИЕ ТЕОРЕТИЧЕСКИЕ СВЕДЕНИЯ О JWT

JWT (JSON Web Token) — открытый стандарт (RFC 7519) для передачи данных между клиентом и сервером в виде компактной строки. В REST API его используют, чтобы после входа не хранить сессию на сервере: нужные сведения уже лежат в токене.

Токен состоит из трёх частей через точку: заголовок (Header), полезная нагрузка (Payload) и подпись (Signature). В заголовке — тип токена и алгоритм, например HS256. В payload — данные пользователя (`id`, `email`) и срок действия. Подпись считается из первых двух частей и секретного ключа сервера `JWT_SECRET`. Если подпись не сходится или срок истёк, токен недействителен.

Пользователь отправляет email и пароль, сервер проверяет их и возвращает JWT. Дальше клиент кладёт токен в заголовок `Authorization: Bearer <token>`. Middleware вызывает `jwt.verify`. Серверу не нужно искать сессию в памяти: подпись проверяется локально.

## 3 ОПИСАНИЕ РЕАЛИЗАЦИИ ДОБАВЛЕННЫХ МЕХАНИЗМОВ

Модель `User` хранит учётные записи в PostgreSQL. Поля: `id` (первичный ключ), `email` (уникальный, обязательный), `passwordHash` (хеш пароля, обязательный), `createdAt`, `updatedAt`. Пароль в открытом виде в базу не пишется. Листинг модели — в приложении А.

### 3.1 Авторизация и аутентификация

Маршруты:

- `POST /auth/register` — принимает `email` и `password`, проверяет сложность пароля и уникальность email, хеширует пароль `bcrypt.hash(password, 10)`, сохраняет пользователя, возвращает 201. Хеш в ответ не отдаётся.
- `POST /auth/login` — ищет пользователя по email, сравнивает пароль через `bcrypt.compare`, выдаёт JWT: `jwt.sign({ id, email }, JWT_SECRET, { expiresIn: '1h' })`.
- `GET /profile` — данные текущего пользователя (id, email, createdAt). Только с токеном.

Маршруты транзакций (`GET/POST/PUT/DELETE /transactions`) тоже закрыты middleware. Категории оставлены открытыми.

Middleware `middleware/auth.js` берёт токен из заголовка `Authorization: Bearer <token>`, проверяет его через `jwt.verify` и кладёт расшифрованные данные в `req.user`. Нет заголовка или токен плохой — статус 401, до контроллера запрос не доходит. Листинг — в приложении Б.

### 3.2 Дополнительный механизм «Проверка сложности пароля»

Для системы учёта личных финансов слабый пароль опасен: учётная запись защищает данные о доходах и расходах. При регистрации пароль проверяется до хеширования:

- длина не меньше 8 символов;
- есть заглавная латинская буква;
- есть цифра;
- есть спецсимвол.

Если правило не выполнено, сервер возвращает 400 и текст ошибки, запись в `Users` не создаётся. Пример неподходящего пароля: `123`. Подходящий: `Secret1!`.

## 5 ОТВЕТЫ НА КОНТРОЛЬНЫЕ ВОПРОСЫ

### 5.1 В чём разница между аутентификацией и авторизацией?

Аутентификация — проверка, кто это (email и пароль при входе). Авторизация — что этому пользователю можно делать (есть ли валидный токен на `/profile` и `/transactions`).

### 5.2 Из каких частей состоит JWT? Как проверить его подлинность на сервере?

Три части через точку: Header, Payload, Signature. Сервер заново считает подпись по Header, Payload и `JWT_SECRET` (`jwt.verify`) и сравнивает с подписью в токене. Плюс проверяет срок `exp`.

### 5.3 Почему пароли нужно хешировать? Что такое соль (salt)?

Хеш необратим: при утечке базы пароль в открытом виде не читается. Соль — случайная добавка к паролю перед хешем, чтобы одинаковые пароли давали разные хеши и не подбирались по готовым таблицам. В bcrypt соль входит в результат `bcrypt.hash(password, 10)`, число 10 — стоимость (число раундов).

### 5.4 Где безопаснее хранить JWT на клиенте (localStorage или httpOnly cookie)? Почему?

Безопаснее httpOnly cookie: скрипт страницы его не прочитает, XSS не украдёт токен. localStorage доступен любому JS на странице. Для лабораторной токен можно временно держать в localStorage, на проде лучше cookie с `httpOnly` и `Secure`.

### 5.5 Как защитить маршрут, доступный только администратору?

Поле `role` у пользователя, роль кладётся в JWT. Middleware после `auth` проверяет `req.user.role === 'admin'`, иначе 403. В этой работе отдельной роли нет: доступ есть у любого вошедшего пользователя.

### 5.6 Как реализовать выход пользователя (logout) при использовании JWT?

Сервер токен не хранит, поэтому «забыть» его сам не может. Клиент удаляет токен из localStorage или cookie. Чтобы отозвать токен раньше срока, нужен чёрный список или счётчик версии сессии в БД.

### 5.7 Какие недостатки имеет хранение JWT в localStorage (уязвимость XSS)?

Любой внедрённый скрипт может прочитать `localStorage` и отправить токен злоумышленнику. Дальше им пользуются, пока не истечёт срок.

### 5.8 Как работает механизм обновления токенов (refresh token)?

Короткий access-токен (минуты) и длинный refresh-токен. Когда access истёк, клиент шлёт refresh на `POST /auth/refresh`, сервер проверяет его (часто он лежит в БД) и выдаёт новую пару. Refresh можно отозвать, access — нет, пока не истечёт.

### 5.9 Как ограничить количество одновременно действующих сессий для одного пользователя?

Хранить сессии в таблице (или `tokenVersion` / список refresh-токенов). При логине, если сессий уже 3, удалять самую старую или отказывать. В JWT класть id сессии и проверять, что она ещё жива.

### 5.10 Как защититься от атак по подбору пароля (brute force) на уровне API?

Лимит запросов на `/auth/login`, задержка, блокировка после нескольких ошибок (`failedLoginAttempts`, `lockUntil`), капча. Плюс сложный пароль — он уже проверяется при регистрации.

### 5.11 Что произойдёт, если скомпрометирован секретный ключ JWT?

Злоумышленник сможет подписывать любые токены. Нужно сменить `JWT_SECRET`: все старые токены сразу станут невалидными, пользователи войдут заново.

### 5.12 Как реализовать временную блокировку учётной записи после неудачных попыток входа?

Поля `failedLoginAttempts` и `lockUntil`. При неверном пароле счётчик растёт; на 5-й раз `lockUntil = сейчас + 5 минут`. Пока время не вышло, вход запрещён. Успешный вход обнуляет счётчик.

### 5.13 В каких заголовках передаётся JWT обычно? Какой формат заголовка?

Заголовок `Authorization`. Формат: `Bearer <token>`.

### 5.14 Как добавить время жизни токена и обеспечить его автоматическое истечение?

В `jwt.sign` опция `expiresIn: '1h'`. В payload попадает `exp`. `jwt.verify` сам отклоняет просроченный токен, отдельный таймер на сервере не нужен.

### 5.15 Можно ли отозвать JWT до истечения его срока? Какие есть подходы?

Сам по себе подписанный JWT живёт до `exp`. Отозвать можно так: чёрный список jti в БД/Redis, версия токена в пользователе (`tokenVersion`), короткий срок жизни плюс refresh, который хранится и удаляется при logout.

### 5.16 Сравните сессионную аутентификацию (с куками) и JWT. Когда что лучше?

Сессия: сервер хранит состояние, cookie — только id сессии. Легко разлогинить, удобно для классического сайта. JWT: сервер не хранит сессию, удобно для REST и нескольких сервисов, но сложнее отозвать токен. Для этого API выбран JWT, как требует задание.

## ПРИЛОЖЕНИЕ Б (обязательное)  
Листинг middleware/auth.js

```js
const jwt = require('jsonwebtoken');
const { HttpError } = require('./errorHandler');

function auth(req, res, next) {
  const header = req.headers.authorization || '';
  const [type, token] = header.split(' ');

  if (type !== 'Bearer' || !token) {
    return next(new HttpError(401, 'Требуется токен'));
  }

  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    next(new HttpError(401, 'Невалидный или истекший токен'));
  }
}

module.exports = auth;
```
